# Commit workflow

Canonical commit procedure. Adapters (thin, link here only):

- [Claude Code skill](../../.claude/skills/commit-changes/SKILL.md): `/commit-changes`; also owns the optional
  sub-agent delegation (Claude Code only)
- [Codex/Cursor skill](../../.agents/skills/commit-changes/SKILL.md)
- [Claude Code rule](../../.claude/rules/finishing-branch-commit-order.md): ordering guard, see
  "Before finishing a development branch"

Commits work from the session change log `changes-log.md`, not from `git diff`. Every script and command below
is verified against the repository; if a mapping names something you cannot find on disk, fix this file before
trusting it.

## Rules

- **Never** `git diff` or `git log` to rediscover what changed. The log is the source of truth. `git status` is
  allowed only in step 1, to find files the log missed.
- **Never** `git add -A` or `git add .`. Stage each path explicitly.
- Never edit a file to make a test, lint, gate, or chart check pass. Report the failure instead.
- Never `--no-verify`, never amend. A failed commit is fixed and re-committed as a new commit.
- Conventional Commits: `<type>(<scope>): <description>`; types `feat fix docs style refactor perf test build ci
  chore revert`.
- HEAD on the shared branch (`main`, `develop`): create a topic branch first unless the user said otherwise.
- After a successful commit, delete `changes-log.md`.
- Use `git -C <path>` instead of `cd <path> && git ...`. Commands you hand the user use the user's shell.
- Combine independent commands into one tool call where a step says so. Every extra call is a full model turn.

Troubleshooting: lint suddenly reporting thousands of ``Delete `␍` `` errors on files you never touched means the
checkout is CRLF (`.gitattributes` pins `eol=lf`, `core.autocrlf` must be `false`): fix the checkout, do not
reformat. A hook failing with `<package manager>: command not found` needs the package manager on the hook's PATH
(for pnpm: `corepack enable pnpm`).

## Before finishing a development branch

Before any step that finishes a branch (a finish-branch skill, opening a pull request, merging, handing the work
over), read `changes-log.md`. Non-empty: run this workflow first, wait until the log is cleared, then proceed. Empty
or missing: proceed directly. Claude Code carries this as a standing rule:
[`.claude/rules/finishing-branch-commit-order.md`](../../.claude/rules/finishing-branch-commit-order.md).

**Why:** this is the repository's only commit path. The log drives the message, tests and builds run before anything
is staged, charts validate when touched, only logged files are staged, and the gate trailers from step 5 are
composed here. Bypassing it leaves the log entries in place, so the next commit message repeats them, and the
unlisted-files guard never runs. Real incident: a sub-agent flow called the finish-branch skill straight after its
own commit and skipped the commit workflow.

## Workflow

### Step 1: read the log and classify `git status` (one call)

```bash
cat changes-log.md; echo "=== status ==="; git status --porcelain
```

- Log empty **and** status clean: tell the user there is nothing to commit and stop.
- Log empty but status dirty: do not assume the changes are yours. Only obvious leftover linter or formatter
  auto-fixes may be committed from the diff; anything else: stop and report the paths.
- `changes-log.md` in `git status`: the ignore rule was removed. Restore it, never commit the log.

**Unlisted-files guard.** Every path in `git status` that is not in the log is classified before staging:

| Class | Example | Action |
|---|---|---|
| Clearly incidental | linter auto-fix to a file already in the log; a lockfile regenerated by a logged dependency change | include, note in the report |
| Everything else | an unrelated modified file; any new file; an untracked directory | **exclude**, continue with the logged files, list the excluded paths in the final report |

Exclude-and-continue is the default in every harness, sub-agent or not: a stopped run throws away the tests and
builds already paid for. Ask the user only when the log names nothing committable. Never stage an untracked
directory on your own judgment; never edit an unlisted file.

### Step 2: test, build, and lint the affected workspaces (one call)

Derive the workspaces from the file paths in the log plus the incidental files from step 1. Record the mapping
from path prefix to workspace filter here once the repository is known:

| Path prefix | Filter | Notes |
|---|---|---|
| `apps/<name>/` | `<workspace name>` | |
| `packages/<name>/` | the package **and** every workspace that consumes it | |
| shared config packages | every workspace | no filter |

Run **one** invocation through the repository's cached task runner (turbo, nx, or the equivalent) with every needed
task and filter, `lint` included, and errors-only output, for example:

```bash
pnpm turbo run test build lint --filter=<workspace> --filter=<workspace> --output-logs=errors-only 2>&1 | tail -60
```

Set the tool timeout to **600 s**: a cold run of several apps takes minutes. Three parts of that line are
load-bearing:

- The task runner, never `pnpm --filter <pkg> test` directly: the direct form bypasses the cache and re-runs the
  suites cold even when the developer session ran the same tests minutes earlier. A cached task is a pass: the
  runner hashes the inputs, so the identical tree already passed. Report it as "cache hit", not "tests ran".
- `lint` in the same call: the pre-commit hook runs lint anyway; here it runs in parallel with the tests and the
  hook then hits the cache.
- Errors-only output: a passing task prints nothing, so the summary line is the whole output; a failing task prints
  its full log. Never re-run to see output; never redirect to a file.

Also:

- Docs-only log (every path ends in `.md`): skip this step and say so; the hook still runs the gates and lint.
- Any failure: **stop**. Report the failing suite or build; do not stage.
- A workspace whose `test` script is a stub (exits 0 without running tests) is reported as "stub". Never report
  "tests pass" when only stubs ran.

### Step 3: validate changed Helm charts

Any path under a chart root (`helmCharts` in `.agent-sdd/config.json`) in the log or in `git status`: run the
Helm validation workflow (`docs/workflows/HELM-VALIDATION-WORKFLOW.md`, installed with the `helm` profile). If you
are a sub-agent, run it inline; never nest sub-agents. Any `FAIL` (lint, template, kubeconform): stop and report; do not fix the chart. A skipped gate is stated
in the report, never implied.

### Step 4: owner-document check (targeted, same commit)

The SPEC-first rules already require the owner document to change with the code, and the `Spec-Impact` gate rejects
a runtime file staged without its owner. This step verifies that cheaply. It is not a document audit.

For each log entry:

- `Spec impact: none - ...`: nothing to read. The reason becomes the `Spec-Impact` trailer in step 5 if the owner is
  not staged.
- `Spec impact: changed`: the owner document (nearest `SPEC.md` upward from the runtime file, else the workspace
  `AGENTS.md`; a split module keeps cross-folder rules in the parent SPEC) must be in the **Files changed** list. If
  it is not: `grep -n` the owner for the symbols or behaviors named in the entry's **What changed** bullets, read
  only the matching lines with context, edit only a real gap, and add the document to the file list. `SPEC.md`
  writes follow the encoding in [FORMAT.md](../agent-sdd/FORMAT.md): match the surrounding density.

Never read a large `AGENTS.md` or a SPEC whole for this step. Root documents (`README.md`, root `AGENTS.md`, the
SPEC-first workflow's coverage table) are touched only when the log says a new document, module, script, command,
or config key was added. A new module without a `SPEC.md`: create it per FORMAT.md and link it from the app
`AGENTS.md` module SPEC table, in this commit, or `scripts/check-docs.mjs` fails. Document edits go into the
**same** commit as the code: a second `docs:` commit runs the whole hook again.

### Step 5: run the gates and compose the message

Run the static gates directly first (seconds; the hook repeats them, but a failure found here costs one turn, not a
failed commit):

```bash
node scripts/check-docs.mjs && node scripts/check-sdd.mjs
```

A gate failure: write the missing document or fix the SPEC shape; never delete the link or the check.

Compose a Conventional Commits message from the log. Terse, exact, why over what.

- Subject `<type>(<scope>): <imperative summary>`, imperative mood (`add`, `fix`, not `added`), at most 50
  characters (hard cap 72), no trailing period. Scope = the workspace when every change falls inside one.
  Type = `feat` if any new feature, `fix` if only bugs, else the majority type. Breaking change: `!` after the scope
  and a `BREAKING CHANGE:` body line.
- Body only when the subject is not self-explanatory: the non-obvious why, migration notes, multi-change commits.
  `-` bullets, each line at most 100 characters (commit linters enforce it; wrap by hand). Always a body for
  breaking changes, security fixes, data migrations, reverts.
- Forbidden: "This commit", "I", "we", "now", "currently", "as requested by", any AI attribution other than the
  `Co-Authored-By` trailer, emoji, restating the file name the scope already says.
- Gate trailers (checked by the commit-msg hook through `node scripts/check-sdd.mjs --staged`, and by CI through
  `--changed`): a runtime file staged without its owner document needs
  `Spec-Impact: none - <at least 8 words naming each file and why behavior cannot change>`. Copy it from the log
  entry. Generic words (refactor, cleanup, no behavior change) are rejected, and **each** such file must be named
  (file name or a folder on its path). A harness file changed without its partner (`.claude/skills/<n>` and
  `.agents/skills/<n>`, `.claude/rules/<n>.md` and `.cursor/rules/<n>.mdc`, the three hook configs) needs
  `Agent-Parity: none - <reason naming each file>`; prefer moving the partner
  ([agent parity workflow](AGENT-PARITY-WORKFLOW.md)). Waivers in `.agent-sdd/waivers.json` are for merged history
  only.
- Line limits: header and **every** body and footer line at most 100 characters, trailers included. A trailer that
  names several files will not fit: **fold** it, continuing on the next line(s) with one leading space, like a Git
  trailer. `check-sdd` joins the folded lines.

  ```text
  Spec-Impact: none - probe.service.ts and projector.service.ts only capitalise finding text
   through sentenceCase; net-tools.dto.ts wording only; scoring untouched.
  ```

Write the message to a file in your scratch directory, then validate it **before** committing (seconds instead of
a failed hook run; the pre-commit lint runs before commit-msg, so a bad trailer used to cost a full lint):

```bash
<commit linter> --edit <scratch>/commit-msg.txt && node scripts/check-sdd.mjs --staged --commit-msg <scratch>/commit-msg.txt
```

`--staged` needs the files staged first: run this right after step 6, before step 7.

### Step 6: stage

`git add <path> ...` for every path under **Files changed** plus the incidental files from step 1, then the message
pre-validation from step 5, in **one** call:

```bash
git add <path> <path> ... && <commit linter> --edit <scratch>/commit-msg.txt && node scripts/check-sdd.mjs --staged --commit-msg <scratch>/commit-msg.txt
```

The staged set is exactly what gets committed; the pre-commit hook re-stages nothing, so other dirty files stay out
without stashing. A trailer or format complaint here: fix the message file and re-run this line; nothing was
committed.

### Step 7: commit

```bash
git commit -F <scratch>/commit-msg.txt
```

The file ends with the `Co-Authored-By: <model name> <noreply@anthropic.com>` trailer for the model actually
running; never copy a name out of this file. Set the tool timeout to **300 s**: the hook runs both gates and then
lint (cache hit after step 2; cold runs take a minute or more).

Hook failure: fix, re-stage, new commit. When a workspace lints without `--fix`, run its `lint:fix` script, then
re-stage.

### Step 8: clear the log and report

```bash
rm changes-log.md && git status --porcelain
```

Report: commit hash and subject; what actually executed in step 2 (per workspace: ran / cache hit / stub / skipped);
chart validation result or "not applicable"; owner documents edited in step 4; paths excluded by the guard.

Commit preparation does not grant permission to push, open a pull request, merge, or delete branches or worktrees.

## Change log format

Append (never overwrite) to `changes-log.md` during the session. A whole-file write on an existing log clobbers
earlier entries. A post-edit hook in each harness config reminds after every edit; the reminder is not the rule,
this section is.

```markdown
## <short description of change group>

**Files changed:**

- `path/to/file.ts`

**What changed:**

- The intent of each change (not the diff); name the symbols

**Spec impact:** changed | none - <concrete reason: which files, why behavior cannot change>
```

One short entry per logical change group. The **Spec impact** line is the draft of the `Spec-Impact` trailer, and
the **What changed** bullets are what step 4 greps the owner document for.
